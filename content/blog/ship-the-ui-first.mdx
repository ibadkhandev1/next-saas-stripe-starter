A blog front end and its admin panel are two different jobs. The first is
mostly reading: a list of posts, a post, some filters. The second is mostly
writing: forms, settings, a place to see who is signed in.

Neither one needs a server to be designed, built, or reviewed. So we kept the
data layer down to a single file and let every component talk to that.

## One seam, not one mock per screen

The tempting version of "mock the data" is to write a fixture inside every
component. It looks local and it works right up until the third screen, when
the same fake user suddenly has two different names and you cannot tell which
one is the real contract.

Instead there is one module, `modules/demo/data.ts`, and every screen reads
from it:

```ts
export function getSession(): { user: DemoUser }
```

and one more for posts, `modules/demo/posts.ts`:

```ts
export function getPosts(): Post[]
export function getTrashedPosts(): Post[]
```

The components never learned that the data is fake. They take a `DemoUser` or a
`Post` and render it, and because the type is the type, the markup that ships
is the markup you keep.

## What that buys you

**The whole app runs with no backend.** Clone it, `npm run dev`, and every
route answers. No database to provision, no OAuth app to register, no storage
bucket to configure. You can work on the reading experience for an afternoon
before you have written a single endpoint.

**The contract is visible.** The type is the API. When you write the real
version, you are filling in a function that already has callers and a return
type — not inventing an interface and then discovering three screens wanted
something slightly different.

**Nothing is stubbed inside a component.** There is no `onClick={() =>
console.log("todo")}` sitting in a form waiting to be found. Every save button
either calls your code or says plainly that it is demo mode.

## The honest parts

Some things are genuinely not demoable, and we left them out rather than fake
them.

There is no sign-out, because there is no session to end — so the header has
Log in and Sign up links, and no logout button that would silently do nothing.

There is no real upload either. Picking a file gives you an object URL that
previews in the browser and nothing more, and the form says exactly that rather
than pretending the file was stored.

Pagination and search run against real content files, so they are real. The
forms update local state and say so in a toast. That line is the whole
discipline: **if it works, it works for real; if it doesn't, the UI says so.**

## Where to start when you wire yours up

`modules/demo/data.ts` and `modules/demo/posts.ts` are the only two files that
have to change. A session, a user and a list of posts. Point them at your API,
keep the return types, and the components keep compiling — which is the entire
argument for putting the seam in one place rather than forty.
